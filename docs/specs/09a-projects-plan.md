## 1. The core idea
A project is an **office document that the vessel contributes to**, and costs are **links to procurement documents, never copies**:

- **Project** is owned by the office: vessel, title, type (Drydock, Non-drydock), superintendent, planned and actual dates, yard (text), the UWILD flag, with its **specification items** (group, description, source, status) as children of the one document.
- **Status is worked out, not stored.** The office adds **status events** (submitted, approved, started, completed, closed, each with a name, a time and a note) and the status (Planning, Approved, Ongoing, Complete, Closed) is the latest one, the same way on both sides, as for risk assessments. A closed project is locked in the service and in the data layer for sync.
- **Budget and costs are the office's commercial data and never go to the vessel.** The vessel receives the project, its specification items (without costs), dates and status. **Budget lines, cost links and cost entries are shore-only.** The vessel can still add to the project (see section 2).
- **Costs are links.** A **project link** names a requisition, purchase order or spot invoice by its global id and says "this belongs to project X". Links are append-only (added, removed), written by whichever side made them, so a link made onboard stays valid ashore. A PO made from a linked requisition is linked automatically. Nothing is added to the PO, requisition or invoice documents, so their owner rules and sync stay as they are.
- **Actual cost is worked out from the links**, in US dollars with the rate already stored on each document (the way the dashboard does spend today), and shown in three columns: **committed** (approved POs), **invoiced** (finalized invoices) and **other** (manual entries, such as a yard bill paid outside the system). A PO that has finalized invoices counts at the invoiced amount instead of its own total, so nothing is counted twice.

## 2. What syncs
| Record | Writer | Direction | Kind |
|---|---|---|---|
| Project with its specification items (no costs) | office | down to the vessel the project is for | document, locked once closed |
| Status event | office | down | append-only |
| Budget lines, cost entries | office | **stay at the office** | shore-only document |
| Project link | the side that made it | both ways | append-only; the office reads the costs behind it, the vessel only sees that the link exists |
| Yard-stay note (date, text, progress percent, optional specification item) | vessel (or office) | both ways | append-only |
| Specification item request (a job the ship asks to be added) | vessel | up | append-only; the office accepts it into the specification or declines |

Lanes: `Transaction` for all of it. Scope: projects of the vessel. Reference code on the existing format (`MVSF-PR-2026-0001`, an H after the year when started ashore). **Files (drawings, reports, photos) wait for the file channel**, as in the other modules; notes carry text only until then.

## 3. Rules
- **Create** needs a vessel with the module switched on, a title and a type. **Who manages projects:** a company admin, or an office user flagged "Project manager" on the Team page (as for Risk reviewer); the superintendent in charge is picked from the office users.
- **First cut approval** is a single action by a project manager: it records who approved, the budget total at that moment and the time. **Tiered approval through the approval matrix** by budget total comes in J7, along with variation orders.
- **Budget vs actual:** variance is budget minus cost to date, and cost to date is committed plus invoiced plus other, using the rule in section 1. Contingency is kept per budget line and shown beside the total, not hidden in it.
- **Specification items** have a source (Worklist task, PMS job, class requirement, owner request, other) and a status (Open, Done, Dropped). Adding from the Worklist or PMS keeps the link, and **an item is never added twice** from the same task or job.
- **From the Worklist:** the vessel's open tasks of the nature a company marks as "deferred to drydock" (a Projects setting; the default is a nature whose name says so) can be added in one action. Marking the item Done adds a completed entry to the task (the Worklist rules about verification still apply). From PMS: due jobs of the vessel can be added the same way; recording the completion stays a PMS action (an item Done shows "record the job as done in PMS" until it is), so the job rules are not bypassed.
- **Close** needs every specification item Done or Dropped and a reconciliation note; it locks the project and puts the closing figures in the history.
- **Module off:** the same gate as the other modules; nothing is shown or accepted for a vessel it is off for.

## 5. Proposed answers to the open decisions (change any you disagree with)
1. **One vessel per project** in this plan, matching the sync scope used elsewhere. A drydock for several vessels is several projects (a shared group name can come later).
2. **Costs are links, and budgets stay at the office.** It protects commercial data and leaves the PO, requisition and invoice documents untouched.
3. **Currency:** budget and reporting in US dollars; documents converted with the rate stored on them, as the dashboard does.
4. **Yard** is a text field now; a yard master and tenders come with the tender work (left for later).
5. **Approval in the first cut** is one named action; the matrix tiers arrive in J7.
6. **Documents checklist and attachments** wait for the file channel; the "missing documents" report goes with them.
7. **PMS completion stays in PMS**, with the project reminding you, so job rules are never bypassed from a project.

## 7. Risks
- **Double counting.** A PO and its invoice describe the same money. The rule in section 1 (a PO with finalized invoices counts at the invoiced amount) is a pure function with its own tests, and the detail page shows the document behind every number so a total can always be checked.
- **Confidentiality.** Budget and cost data must never reach a vessel. J1 builds the shore-only kind first and tests it before any screen depends on it; if the publisher cannot hold such a kind, it is extended in J1.
- **Links to documents that change.** A linked PO may be rejected or a linked invoice rejected after the fact; costs are worked out from the current state of each document, never stored on the link.
- **Currency.** A document with no stored rate is counted at its own amount, as the dashboard does today, and the detail page says so plainly.
- **Closed means closed.** Enforced in the service and in the data layer for sync, with a test that tries every edit path, as for the other modules.
- **Duplicate imports.** Each specification item remembers the task or job it came from, so importing twice adds nothing.

## 8. Decisions made while building J1
- **Status events** are Approved, Started, Completed, Closed and Withdrawn (an approval taken back, only before work starts). "Submitted" comes with the matrix tiers in J7. The steps must follow in order, and a project can only move forward from where it is.
- **Actual dates are the dates on the Started and Completed events**, which the office enters (the day the ship reached the yard may be earlier than the day it was recorded). The project itself holds only the planned dates.
- **Money never leaves the office.** The project, its items, status events, notes and links are registered for sync; budget lines, item estimates, cost entries and the approved totals are ordinary tables that are not registered, so nothing is ever published for them and a vessel installation refuses to write them. A vessel starts from an empty database, so none can arrive by copying either. Two tests prove it: a vessel holds none, and cannot create one.
- **What was approved is kept.** Approving writes the budget total (and contingency) at that moment beside the event, so withdrawing, changing the budget and approving again leaves both figures on record.
- **Specification items are marked Done or Dropped by the office** (saving the specification); the vessel reports progress in notes. Removing an item removes its estimate.
- **Who may do what** is not decided in the service yet: the "Project manager" permission arrives with the screens in J3, as the Risk reviewer flag did in R4. Onboard, the service refuses everything except notes and links.
- **Links** can name a requisition, an order or an invoice. The vessel holds its own requisitions and orders but not invoices (they are office business), so only the office can link an invoice. A document belongs to the project of its latest link; linking it to another project moves it, and saying the same thing twice changes nothing.
- **Closed means closed** for everything: items, budget, cost entries, notes and links are refused, on both sides, and a changed copy of a closed project arriving by sync is ignored.

## 9. Decisions made while building J2
- **Orders and invoices inherit their project instead of being linked when they are raised.** An order with no link of its own belongs to the project of its requisition, and an invoice to that of its order; a link written on the document itself always wins, and a removal means "none", not "back to the requisition's". Reading it this way covers every way an order can be raised (from an RFQ, a spot order, onboard, handed over) without a hook in each, and the panel says "through its requisition" so nobody is surprised. Linking an order outright (`LinkAsync`) pins it, so it stays put if its requisition is later moved.
- **What counts as cost.** An order counts when it is Approved and not record-only; an invoice counts when it is Finalized, at its total before tax (the figure the approval matrix compares). A pending, rejected or record-only order, and an invoice not yet finalized, are listed but not counted, with the reason. The rest follows the rule in section 1 (an order with finalized invoices counts at the invoiced amount).
- **Currency.** In US dollars with the rate stored on the document, else the company's rate for its date, as the dashboard does. With no rate at all the document is counted at its own amount and reported as unconverted, so the figure is never silently wrong.
- **Cost is read at the office only.** A vessel installation refuses the rollup, as it holds no invoices and must not see money.
- **Where it is shown.** Every requisition, order (office and onboard) and invoice page has a Project panel when the module is on for the vessel and there is a project to show or choose; a closed project is not offered. The forms for a new requisition, spot order and spot invoice ask for the project beside the vessel and link the document once it is saved. The cost figures themselves are shown with the project screens in J3.
- **Not seen in a browser yet:** the panel on a requisition, an order and an invoice was checked (including "through its requisition" and "through its purchase order"); the project choice on the three forms was built but not looked at, as no project can be created from the screens until J3.

## 10. Decisions made while building J3
- **Project manager** is a flag on the user, set on the Team page, exactly like the Risk reviewer flag (one added column, an additive migration). A company admin always is one. It is enforced in the service, not only on the screens: create, edit, specification, budget, estimates, cost entries and every status step refuse anyone else ("Only a company admin or a project manager can do this"). Reading a project, adding notes and linking documents need no special right. A vessel installation never plans projects.
- **Budget, estimates and cost are shown to every office user**, who already see the orders and invoices behind them; only managers can change them. They are never sent to a vessel.
- **One page per project** (`/projects/{id}`) with its sections one under another rather than tabs: next steps and details at the top, then specification, budget, cost, notes, history. The next-step buttons follow the status (Approve; Start work or Withdraw approval; Mark work complete; Close project), each asking for the date it took effect and a note, and closing for the reconciliation note.
- **List.** Filters for vessel, superintendent, year, search and status (the status buttons show how many each gives); columns for dates, days (actual of planned), items done of all, budget, cost to date and variance, red when over. Over budget only means something once a budget is set, so a project with cost and no budget is not flagged. The dashboard's card links straight to a status.
- **Dashboard card** (office only): Ongoing, Not started (planning or approved, since an approved project waiting for the yard would otherwise count nowhere) and Over budget, which also feeds the attention strip. Closed projects are history and are not counted.
- **Menu and finder.** A "Projects" group appears for the office when the module is on, with "New project" shown only to those who may plan one; typing "drydock", "yard" or "project" in the finder finds it. Onboard menus and screens come with J5.
- **Checked in a browser**, creating a project through the form and building it up: specification with estimates, budget, approval (the approved total is shown), an order put on the project through its own page (committed cost appeared, and its invoice was listed as not counted yet), the list, the menu, the finder, the dashboard card and the Team page column. Not yet looked at: the next steps after approval (start, complete, close) and the notes form in a browser; they are covered by the service tests.

## 11. Decisions made while building J4
- **The "deferred to drydock" nature.** The standard Worklist natures (Planned, Emergency, Deferred, Survey, Recommendation, Condition) say nothing about drydock, so the plan's default (a nature whose name says so) finds nothing in a new company. A company admin therefore chooses the nature on the import panel itself (one column on the company, an additive migration); until then no tasks are offered and the panel says so. If the admin names a nature "Deferred to drydock" (also "Dry-Dock", "dry dock") and has not chosen one, that one is used. Choosing none goes back to looking by name.
- **What is offered.** Tasks: the vessel's open tasks (not completed or cancelled) of that nature. Jobs: the vessel's active maintenance jobs due within a window the manager sets (90 days to begin with; an overdue job always counts; a job with no due date never does). Anything already on this project's specification is left out, and each item remembers its task or job, so adding the same one twice adds nothing and says so.
- **The link back.** A task that is added gets a Link entry on its own timeline ("Project SF-PR-…"), so the task page shows "Linked" with a link to the project, and the entry reaches the vessel's copy of the task. Onboard that link has nowhere to go until the vessel's project screens (J5). A maintenance job gets no entry here; its item on the specification links to the job.
- **Done closes the task, once.** Saving an item as Done when it was not Done before adds a Completed entry ("Done at the yard (project …)") to its task. A task already completed or cancelled is left alone, reopening and marking Done again does nothing more, and a task whose source needs the office to verify it is completed but still waits for that, which the message says. Dropping an item does nothing to its task.
- **Maintenance is never completed from a project.** A Done maintenance job on the specification shows "Record the job as done in maintenance" until a completion has been recorded for it since the work began (the day work started, else the planned start, else the day the project was created). The job's own rules therefore apply.
- **Who.** Importing, like every other change to a specification, is for a project manager; choosing the nature is for a company admin.
- **Checked in a browser** with a real task: choosing the nature, importing the task, the item and its link to the task, marking it Done (the task became completed with the note), and the task page showing the link to the project. The maintenance side was tested by the service tests only, as the demo company has no maintenance jobs.

## 12. Decisions made while building J5
- **One set of pages, two faces.** `/projects` and `/projects/{id}` are the same pages onboard and ashore (both marked as allowed on a vessel, and added to the lockdown test's list). Onboard they show the heading "Vessel", the specification, days, status, notes and requests; the budget, cost, estimates, approvals and every office button are simply not there, and the data is not either: the list and counts leave the money empty, and the service reads none onboard. The planning screens (`/projects/new`) stay office only.
- **Requests.** The vessel asks for another job on a project that is not closed: the job, and what was found and where. It is written once and cannot be changed (a request is history), and goes up like a note. The office answers it once: **Add to the specification** (under a group it can change, "Vessel requests" to begin with; the job joins the specification as an ordinary item whose source says "Vessel request", and the answer names that item) or **Decline** with a reason. Only a project manager answers, and only ashore. A request on a project that is later closed stays as it was.
- **Both sides see the same story.** The answer comes down with the specification (the new item travels with the project, the answer as its own record), so the vessel's list of requests shows Waiting, Added to the specification or Declined with the reason. The office's card on the dashboard counts the requests waiting and the attention strip carries it ("vessel requests to answer"); the vessel's card shows its own count, as information only.
- **Menu and finder onboard** now include the Projects group, with only "Projects" (no "New project"). A Worklist task that was added to a project now links to it from onboard too.
- **Notes need nothing new:** the vessel already wrote notes in J1; the form is on the same page, with large fields for a tablet, and notes arrive in order as before.
- **Checked in a browser** by running the app in vessel mode on the same database for a few minutes (the stored node profile was switched to Vessel and then back): the vessel list and page without money, sending a request, then the office page showing it, answering it, and the specification gaining the job. Not checked that way: two real installations syncing (the two-database tests do that), and a phone-sized view.
